# 08 · 逐功能点测试闸门（新增规则一）

> **定位**：把 `general/principles.md` 第 2 节的"完成即测"从原则升级为**可检查、留证据、卡进度**的硬闸门。
> **触发**：任何一次功能开发、改状态机、加接口、改交互、修 bug。
> **配套**：`.agent/workflow/features.json`（功能点清单）、`scripts/feature_gate.py`（执行器）、`.agent/workflow/progress.md`（进度）、`general/unit-test.md`（单测要求）。

## 1. 一句话规则

**AI 开发完一个功能点后，必须立刻测试这个功能点有没有问题；测试结果 `PASS` 之前，禁止进入下一阶段、禁止开始下一个功能点。**

这不是"最后统一跑一遍 `go test`"，而是**每个功能点各自跑一次闸门**，且闸门结果落盘留证。

## 2. 功能点状态机

| 状态 | 含义 | 允许的动作 |
| --- | --- | --- |
| `未开始` | 清单中待开发 | 取该点（须前置功能点全部 `已通过`） |
| `开发中` | 正在写实现与单测 | 只允许改本功能点涉及的模块 |
| `待验证` | 代码写完，尚未跑闸门 | **只能跑闸门**，不得开新功能点 |
| `闸门失败` | 测试未通过 | 写 `issue-log` → 修复 → 回到 `待验证` |
| `已通过` | 闸门 `PASS` 且证据落盘 | 更新 `progress.md`、提交，然后才能取下一个功能点 |

合法迁移只有：`未开始 → 开发中 → 待验证 → (闸门失败 → 待验证)* → 已通过`。
**禁止** `待验证 → 开发中(下一个功能点)`、`闸门失败 → 已通过`、`未开始 → 已通过`。

## 3. 闸门检查项（缺一即 FAIL）

| # | 检查项 | 判定方式 |
| --- | --- | --- |
| S1 | 前置功能点全部 `已通过` | 读 `.agent/workflow/gate-records/<前置ID>.json` 的 `result == PASS` |
| S2 | 本功能点涉及的**每个模块都有单元测试** | `scripts/check_module_tests.py`，逐包检查 `*_test.go` 存在且非空 |
| S3 | 该功能点的专项单测存在 | `features.json` 中 `test_files` 逐个存在 |
| S4 | 格式与静态检查 | `gofmt -l` 无输出；`go vet ./...` 退出码 0 |
| S5 | 功能点测试通过 | `go test -race -count=1 -run '<该点正则>' <模块包>` 退出码 0，且**至少命中 1 个测试**（"0 tests ran" 视为 FAIL） |
| S6 | 覆盖率不回退（阶段/交付点） | `make coverage`，整体与核心业务包 ≥85%（沿用 `scripts/coverage_gate.py`） |
| S7 | 场景断言（交付点） | `scripts/acceptance_check.py` 五大场景 48 项断言全 PASS（需服务已启动） |
| S8 | 证据落盘 | 写 `.agent/workflow/gate-records/<ID>.json`：时间、功能点、命令、退出码、输出摘要 |

> `features.json` 中 `type: "unit"` 的功能点执行 S1–S5、S8；`type: "gate"`（覆盖率 / 验收 / 全量回归）额外执行 S6/S7。

## 4. 证据格式（脚本自动生成，AI 不得手改）

```json
{
  "feature": "F3.1",
  "result": "PASS",
  "at": "2026-11-13T10:20:00+08:00",
  "checks": [{"name": "unit_tests", "cmd": "...", "exit": 0}],
  "tests_hit": 12,
  "notes": "前置 F1.1/F2.1 已通过"
}
```

**"已测过"只认这个文件**。口头说"我测过了""应该没问题"一律不算；`progress.md` 的状态必须与证据文件一致。

## 5. 失败处理（强制顺序）

1. 闸门 `FAIL` → **立刻停止**，不碰下一个功能点的任何文件。
2. 按 `general/issue-log.md` 模板追加一条：现象、复现步骤、根因、解决、是否上升为约束、关联需求/状态机迁移。
3. 只修本功能点的问题；若修复暴露规则漏洞，同步补进 `backend/constraints.md` / `frontend/code-style.md`（既有闭环）。
4. **原功能点重跑闸门**，直到 `PASS`。禁止用"改断言""跳过依赖""注释测试""改脚本阈值"换绿灯。
5. 回填 issue-log 的"解决"字段。

## 6. 明确禁止（违反即本次交付作废）

| 禁止行为 | 为什么 |
| --- | --- |
| 写完 3 个功能点再一起测 | 违反 `principles.md` 闭环优先，且失败时无法定位是哪个改动引入 |
| 测试没过就说"已完成/已通过" | `principles.md` 第 2 节"不伪造结果" |
| 用 `--skip-deps`、`--skip-tests` 或改 `features.json` 绕过 | 闸门失去意义 |
| 只跑 `go build` 当测试通过 | 编译 ≠ 功能正确 |
| 用 `-run` 拼一个不存在的正则制造 "0 tests PASS" | 脚本已把 0 命中判为 FAIL |
| 闸门失败期间顺手改别的模块 | 污染定位，且扩大范围 |

## 7. 与既有文件的分工

| 文件 | 管什么 |
| --- | --- |
| `general/principles.md` | 总纲：闭环优先、增量开发、不伪造结果（原则层） |
| **本文件 `feature-gate.md`** | **逐功能点的状态机、检查项、证据、失败处理（执行层）** |
| `general/unit-test.md` | 哪些模块必须有单测、怎么写、覆盖率门槛 |
| `general/acceptance.md` | 提交前通用门槛 + 五大场景断言清单 |
| `scripts/feature_gate.py` | 把上述规则变成一条命令与一个退出码 |
